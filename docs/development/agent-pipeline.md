# Агентский конвейер разработки

## Принцип работы

Один оркестратор ведёт пользовательскую задачу от решения до проверенного результата. Он разбивает работу, назначает владельцев, не даёт параллельным агентам конфликтовать и принимает доказательства, а не декларации. Специалисты не меняют утверждённые продуктовые решения и не расширяют scope.

В работе одновременно могут быть несколько независимых исследований, но изменяемая поверхность всегда имеет одного владельца. «Поверхность» — файл, модуль, миграция, API-контракт, конфигурация deployment или набор тесно связанных файлов. Если пересечение неочевидно, работа идёт последовательно.

## Роли

| Роль | Отвечает за | Не имеет права | Артефакт передачи |
| --- | --- | --- | --- |
| Оркестратор | декомпозиция, порядок, границы, итоговая интеграция и приёмка | выдавать предположения за решение пользователя | план, ownership map, итоговое доказательство |
| Product analyst | пользовательские сценарии, поля, состояния, исключения, решения | придумывать функции за пределами запроса | обновление product rules, открытые решения |
| Architect | домены, данные, API, миграции, угрозы, integrations | писать большой несогласованный код | ADR/architecture proposal, schema/API checklist |
| Implementer | один согласованный вертикальный slice и его тесты | менять чужие модули или бизнес-правила молча | diff, тесты, миграции, handoff |
| Test engineer | требования, негативные случаи, интеграция, runtime proof | принимать собственную непроверенную реализацию | test matrix, результаты, найденные риски |
| Reviewer | независимый audit diff, безопасность, регрессии, docs | переписывать решение вместо конкретного review | findings с severity и evidence |

Project-scoped варианты этих ролей лежат в `.codex/agents/`. Они задают поведение агента, но не отменяют `AGENTS.md` и правила проекта.

## Шаблон постановки подзадачи

Каждому агенту передаётся только необходимый контекст и следующий контракт:

```text
Goal: [один результат]
Context: [ссылки на docs и реальные файлы]
Owned surface: [модули/файлы, которые может менять; или read-only]
Non-goals: [что сознательно не делать]
Constraints: [совместимость, privacy, security, product invariants]
Done when: [наблюдаемые критерии и команды проверки]
Report: [изменения, evidence, риски, открытые вопросы]
```

Нельзя назначать «сделай backend» или «посмотри всё». Такие задачи сначала декомпозирует оркестратор. Агент при недостатке критичного решения задаёт один точный вопрос либо фиксирует блокер, а не подменяет решение собственной догадкой.

## Этапы

### 0. Intake и классификация риска

Оркестратор читает `AGENTS.md`, существующий код и релевантные документы. Затем определяет: затрагиваются ли деньги, PII, auth, миграции, вебхуки, публичный API, production или удаление данных. Для любого из них обязательны архитектор и независимая проверка; для необратимого внешнего действия — явное человеческое подтверждение.

### 1. Discovery (параллельно, только read-only)

Независимо можно поручить: инвентаризацию кода, проверку первичных документов провайдера, тестовый аудит, анализ дизайна или security threat-model. Каждый агент возвращает конкретные пути/источники и выводы, не правки. Оркестратор синтезирует противоречия в один список решений.

### 2. Спецификация и архитектурный gate

Product analyst фиксирует exact user flow, данные, состояния и вне-scope. Architect фиксирует ownership данных, API, миграции, failure modes, idempotency и observability. Оркестратор сверяет с `docs/product/business-rules.md` и `docs/architecture/*`.

Если меняются утверждённые правила (например, появляется частичный возврат, другой статус заказа, карта в форме или supplier integration), работа останавливается для решения пользователя. Для согласованных крупных работ пишется пошаговый implementation plan с путями, тестами и порядком зависимостей.

### 3. Реализация

Оркестратор назначает один vertical slice одному implementer-у. Порядок для этого проекта обычно такой:

1. schema/migration и server-side domain rules;
2. API contracts и integration ports;
3. webhook/outbox/worker;
4. frontend typed API client, auth/session и пользовательский flow;
5. visual adaptation и accessiblity;
6. observability/configuration.

Implementation начинается с теста или другой воспроизводимой проверки поведения. Агент меняет только назначенную поверхность, делает малые понятные патчи, не вставляет ключи/PII/mock bypass. Он не считает redirect от Arc успешной оплатой и не создаёт notification напрямую в endpoint.

### 4. Самопроверка implementer-а

До передачи агент запускает релевантные unit/integration tests, typecheck/lint/build в соответствующем приложении и проверяет миграцию на чистой БД, если она есть. Для UI проверяет реальный сценарий браузером. Он прикладывает точные команды, выход/результат и честно перечисляет непроверенное.

### 5. Независимая проверка

Test engineer получает спецификацию и diff, а не только резюме implementer-а. Проверяет happy path и как минимум один негативный/повторный случай для каждого риска:

- повтор запроса/вебхука не создаёт второй платёж, заказ, возврат или уведомление;
- неавторизованный пользователь не получает историю/checkout;
- изменённая цена на клиенте не принимается;
- неверная Arc подпись не меняет состояние;
- `booking` не создаёт оплату;
- возврат не меняет `is_processed`;
- worker retry не дублирует письмо/Slack.

Reviewer отдельно читает final diff на соответствие архитектуре, секреты, PII, N+1/transaction boundaries, error handling и актуальность документации. Замечания классифицируются: blocker / required / follow-up с путём и причиной.

### 6. Интеграция и приёмка

Оркестратор устраняет необходимые замечания через владельца поверхности, повторяет затронутые проверки и подтверждает Definition of Done из задачи. Только после evidence можно говорить «готово». Если есть Git, следующая ступень — отдельный commit, review и защищённое слияние; в текущей директории Git пока не инициализирован, поэтому коммиты не имитируются.

## Очередь и параллельность

```text
Intake
  → read-only discovery (parallel)
  → product + architecture decision (single synthesis)
  → implementation plan (single)
  → independent slices (parallel only if no shared surface)
  → implementer checks
  → test engineer + reviewer (parallel read-only)
  → fixes (single owner)
  → final verification and handoff
```

Нельзя параллельно:

- менять migration и модель, которую она вводит;
- менять один API schema/client contract без согласованного владельца;
- писать в одну директорию frontend feature;
- выполнять два платежных/refund эксперимента на одном внешнем объекте;
- чинить review замечания до того, как оркестратор выбрал владельца.

Можно параллельно: исследовать Arc и Resend, инвентаризировать frontend и backend, проектировать тест-кейсы по уже замороженной спецификации, проводить read-only security/code review разных модулей.

## Handoff без потери контекста

Каждая передача заканчивается шестью пунктами:

1. результат и затронутые пути;
2. принятые/непринятые решения;
3. команды проверки и итог;
4. известные риски и непроверенные границы;
5. что должен сделать следующий владелец;
6. ссылки на документы/issue/contract.

Передавать длинные скрытые рассуждения, секреты, дампы PII и «вроде работает» нельзя. Оркестратор хранит сжатое решение в docs/плане, чтобы следующий агент не зависел от чата.

## Условия остановки и эскалации

Остановиться и запросить решение нужно при: неизвестной правовой/финансовой политике, отсутствии нужных Arc/Resend/Slack секретов, конфликте требований, destructive миграции, production действии, изменении общей админки, трёх повторных одинаковых технических сбоях либо невозможности доказать заявленное поведение. Нельзя обходить блокер fake payment, mock success или отключением проверки подписи.
