# Managed Directions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Turkiye directions authoritative, editable in VV Admin and visible as real, ordered product collections on the public site.

**Architecture:** Turkiye's existing catalog module gains `destinations` and
an ordered `product_destinations` relation. The protected Turkiye Admin API is
extended, then surfaced through the capability-gated `turkiye_v1` VV Admin
connector. The public frontend uses the new public catalog endpoints at
request time; the design-source import creates only the approved initial data
through the Admin API.

**Tech Stack:** NestJS/Fastify, Drizzle/PostgreSQL, MinIO/S3 media,
Next.js 16/React 19, TypeScript, Vitest, pnpm workspace, Node test runner.

## Global Constraints

- Categories remain exactly two levels and are never used for geography.
- A direction is public only when it is active and contains at least one
  active product in an active category.
- A product can belong to zero or more directions; the join record owns its
  `sortOrder`.
- All Turkiye mutations use its protected Admin API and trusted actor ID;
  neither VV Admin browser nor frontend receives Turkiye or MinIO credentials.
- Direction cover uploads accept exactly one JPEG, PNG or WebP of at most
  5,242,880 bytes and are generated WebP objects below `destinations/`.
- Do not alter product checkout, booking, payment, refund, order or outbox
  semantics.
- Preserve unrelated work; stage only paths owned by the current task. Do not
  deploy or import production data without a separate explicit approval.

    id: uuid('id').defaultRandom().primaryKey(),

    region: text('region').notNull(),
