# Импорт каталога дизайна в production: дизайн

## Контракт

**Goal:** перенести 93 позиции из утверждённого дизайна Turkiye в production-каталог через Admin API, с одной локальной фотографией у каждого товара.

**Context:** источником позиций служит `frontend/src/data/marketplace-sources.ts`. Его SHA-256 совпадает с файлом `main` публичного репозитория, из которого опубликован `https://avvolkova13.github.io/turkiye/`. Production-каталог уже поддерживает категории глубиной два уровня, товары, audit trail и загрузку одного фото в MinIO.

**Constraints:**

- Не изменять или удалять существующие production-категории и товары.
- Использовать только Admin API; не писать напрямую в PostgreSQL или MinIO.
- Все деньги хранить в minor units `RUB`; источником рублёвой цены является значение, отображаемое дизайном.
- В один товар загружается ровно одно локальное изображение; входной файл не должен превышать 5 MiB.
- Не копировать URL, метаданные или снимки сторонних поставщиков в production-каталог.
- Повторный запуск безопасен: уже импортированные slug не перезаписываются, а конфликт фиксируется в отчёте и завершает запуск ошибкой.

**Done when:** созданы 10 корневых категорий, 3 подкатегории и 93 товара, у каждого есть изображение, согласованные тип/цена/валюта, а публичный API возвращает активный каталог.

## Источник и граница данных

Импорт использует только следующие поля каждого `sourceProducts`:

- `id` как production `slug`;
- `title` и `description`;
- рублёвую цену из округления `sourcePrice * eurToRub`, используемого дизайном;
- `imagePath` из `frontend/public/images`;
- `type` и `subcategory` для назначения категории.

Поле `sourceUrl`, имя поставщика, дата snapshot, provider status и пользовательские demo-поля прототипа не переносятся. Они не входят в утверждённую production-модель.

## Категории

Создаются десять активных корневых категорий с теми же name/slug, что в дизайне:

| slug | name |
| --- | --- |
| `excursions` | Туры |
| `tickets` | Билеты в музеи и достопримечательности |
| `activities` | Впечатления и экскурсии |
| `restaurants` | Рестораны |
| `spa` | Красота и wellness |
| `connectivity` | eSIM |
| `transfers` | Трансферы |
| `digital` | Проездные |
| `shopping` | Шопинг |
| `vip-transport` | VIP транспорт |

Подкатегории создаются только там, где они заданы самими позициями:

| parent slug | slug | name |
| --- | --- | --- |
| `shopping` | `shopping-fur` | Меха |
| `shopping` | `shopping-jewelry` | Ювелирные изделия |
| `vip-transport` | `vip-transport-helicopters` | Вертолёты |

Товары без `subcategory` ссылаются на корневую категорию. Три позиции `guides`, которых нет в списке корневых категорий дизайна, ссылаются на `activities`.

## Типы и цены товаров

Назначение типа определено пользователем:

| Набор позиций | Production type | Цена |
| --- | --- | --- |
| `connectivity`, `tickets`, `digital`, `guides` | `auto_delivery` | обязательная, в `RUB` minor units |
| `shopping` | `physical` | обязательная, в `RUB` minor units |
| `excursions`, `activities`, `restaurants`, `spa`, `transfers`, `vip-transport` | `booking` | обязательная справочная цена в `RUB` minor units; checkout не создаётся |

У booking-позиций цена нужна для точного отображения каталога. Она не создаёт payment intent и не меняет утверждённый flow: пользователь отправляет заявку, а менеджер подтверждает детали вручную.

## Изображения

Каждый товар получает фотографию, указанную в `imagePath`. Импорт передаёт её в multipart-поле `photo` Admin API. API принимает JPEG, PNG или WebP до 5 MiB, проверяет декодирование и нормализует результат в WebP в MinIO.

Перед отправкой импорт проверяет локальный размер и формат. Два
исключительных ассета преобразуются во временный WebP без изменения
дизайнерских исходников: `catalog-generated/bursa-koza-han-market.jpg`
(6,154,618 bytes, выше лимита) и `home-sources/cappadocia-cave-hotel.avif`
(единственный AVIF, который API намеренно не принимает). Оба результата не
превышают 5 MiB до отправки как фото соответствующего товара.

## Импорт и идемпотентность

Скрипт сначала читает текущие категории и товары через Admin API с отдельным audit actor `catalog-import-2026-08-10`. Затем он:

1. создаёт отсутствующие категории в порядке root → child;
2. создаёт отсутствующие товары в порядке исходного массива;
3. останавливается при любом уже занятом slug, который не принадлежит такому же импортируемому объекту;
4. пишет в stdout только обезличенный итог: создано, уже существует, конфликтов, неудачных загрузок.

Существующие production записи, включая тестовые `category1`, `undercategory1` и `cat`, не изменяются.

## Проверка

После импорта скрипт повторно читает Admin API и проверяет:

- все ожидаемые category/product slug существуют и активны;
- всего создано 10 root и 3 child categories с корректными parentId;
- всего импортировано 93 товара;
- у каждого из 93 товаров есть `priceMinor` и `RUB`; наличие цены у `booking` не создаёт checkout;
- у каждого товара есть URL `/media/products/...webp` и URL возвращает `200`;
- публичный API каталога выдаёт 93 импортированных активных товара.

Для runtime-подтверждения дополнительно открывается публичная страница одного товара из каждого из трёх type-наборов и проверяется загрузка фото.
